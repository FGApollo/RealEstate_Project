# Authentication rollout

1. Apply missing migrations in order: `003-auth-sessions.sql`, `004-google-identities.sql`, `005-otp-send-rate-limit.sql`, then `006-email-verification.sql`. Confirm `users.id` is an integer and the migrations succeed. The email migration intentionally fails if existing emails collide after lowercasing/trimming; resolve those accounts deliberately, never auto-merge them. It grandfathers accounts that exist at migration time as email-verified for compatibility. Do not expose `auth_sessions`, `google_identities`, or `email_verification_tokens` through public Supabase policies.
2. Configure the server-only values in `.env.example` in the backend's secret manager. Generate `JWT_SECRET` as a high-entropy random secret (at least 32 bytes). Never use `VITE_` for the service-role key or JWT secret. Rotate any service-role key previously exposed to a browser.
3. Set `CORS_ALLOWED_ORIGINS` to a comma-separated list of exact frontend origins. Development may use `http://localhost:5173,http://127.0.0.1:5173`; production should contain only its deployed frontend origin, and preview origins should be configured only on a staging service. `CLIENT_ORIGINS` remains a temporary legacy alias. For a cross-site frontend/backend pair, use `AUTH_COOKIE_SAME_SITE=none` and HTTPS (`Secure` is then enforced). For same-site deployments, `lax` is sufficient.
4. Configure `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, `GMAIL_SENDER_EMAIL`, and the exact `FRONTEND_URL` in the backend secret manager. The OAuth grant must include only the Gmail `gmail.send` scope, and the sender must match the Gmail account that granted it (or an alias configured in that mailbox). Never put OAuth secrets or refresh tokens in frontend `VITE_` variables. Google OAuth apps left in Testing can have refresh tokens expire after seven days; monitor/renew the grant or complete the required Google verification before relying on long-lived production delivery.
5. Configure the frontend `VITE_API_URL` to the backend origin. Rebuild and deploy the frontend with the backend. Existing `localStorage.user` values are display cache only and do not authorize requests; users must sign in again because the old login issued no refresh cookie.
6. Set the same Google OAuth web client ID in server `GOOGLE_CLIENT_ID` and frontend `VITE_GOOGLE_CLIENT_ID`, configure its authorized JavaScript origins, and use the Google ID-token button flow. Old frontend builds sending Google access tokens to `/api/google-login` are no longer compatible.
7. Restart the backend and run `npm run build` in the project root and `npm test --prefix server`. Exercise password USER/AGENT registration, email verification, Google registration/login, existing-account linking, refresh, logout, and protected APIs against a staging database before production rollout.

Access JWTs use HS256, issuer/audience verification, a 15-minute lifetime, and only `sub`, `sid`, `token_use`, `jti` plus standard JWT claims. `req.user` is reloaded from the database on every protected request, so role changes take effect immediately. An opaque, hashed, rotating refresh token is stored in `auth_sessions` for seven days and sent only as an HttpOnly cookie scoped to `/api/auth`. Logout revokes that session. Invalid or expired access tokens receive 401; authenticated callers with the wrong role receive 403.

Paid subscription activation is intentionally disabled until a verified payment integration exists. The old client-controlled `price_vnd`, `status`, and duration path was unsafe. This rollout also does not make publicly hosted KYC documents private: review the `kycService` Storage bucket configuration and migrate identity documents to a private bucket with short-lived signed URLs separately.

Google login now accepts a server-verified ID token and explicit `LOGIN`, `USER_SIGNUP`, or `AGENT_SIGNUP` intent. Intent never changes an existing user's DB role. New Agent accounts require a phone; their KYC state remains separate from email verification. Existing accounts with authoritative Gmail/Workspace addresses are linked on first Google login. For a third-party email without a Workspace `hd` claim, an existing password account must confirm its password before Google is linked; new Google provisioning for that domain is rejected. Such users can register with a password, verify the address, then link Google by confirming the password. Legacy Google-only accounts with such email addresses need a manual recovery/linking process because they have no account password. Already-linked Google subjects can continue to log in. The migration records Google subjects; do not backfill them from email alone.

Password registrations create accounts with `email_verified_at = NULL` and issue a 256-bit, 24-hour single-use verification token; only its SHA-256 hash is stored. Verification is confirmed by an explicit user click on the frontend, then the backend atomically consumes the token. Password login and protected API access require verified email. Google login uses the server-verified Google `email_verified` claim and does not send a second email. Agent KYC remains independent of email verification.

The public register/resend messages do not confirm whether an email exists. Gmail API delivery over HTTPS is started asynchronously so response content/timing does not wait on Google; delivery failures are logged only by error code, and the user can request a resend after the cooldown. This is not a durable outbox, so monitor backend logs and the sender mailbox's delivery/bounce signals.

Password registration also uses `USER_SIGNUP` or `AGENT_SIGNUP` intent now. The backend rejects a raw `role` field on both registration and Google endpoints; older frontend builds that send `role: AGENT` to `/api/register` must be replaced with this frontend during rollout.
